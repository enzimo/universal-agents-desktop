# Desktop 0.4.4 Windows build validation

## Review judgment

Goal alignment: the native Windows installers select UA 0.4.4 and retain the reviewed runtime-update flow. Consequence risk: moderate, because UA 0.4.4 changes active-task storage without migration. Evidence is strong for native compilation, update authorization and isolated runtime onboarding; real account login, chat and upgrades of existing user data still require manual acceptance.

The baseline is desktop commit `d4de207`, version 0.4.3 with UA 0.4.2. This review covers the Windows/Linux host adaptations, the Windows test manifest, the new runtime digest, and initialization of the saved runtime selection. It does not certify a production-signed installer or migration of UA-owned data.

## Evidence

- Windows 11 x64: 50 core and 6 application Rust tests passed, Clippy passed, and all 11 launcher JavaScript tests passed. Native NSIS and MSI packaging succeeded.
- macOS: the same 56 Rust tests, Clippy and 11 UI tests passed. The actual Tauri application compiled locally. GitHub-hosted macOS CI remains subject to the existing account billing restriction.
- The Windows popup probe passed in the signed-in desktop. Both immediate and deferred child navigation shared cookies and denied desktop commands. Its initial `0xc0000139` failure was traced to the example's missing Common Controls v6 manifest and reproduced before the build-script fix.
- The image was built from UA's GitHub-verified signed `v0.4.4` tag at `a14fcbfad3062c621149c443d9918057f9827e0f`. The combined GHCR digest contains Linux amd64 and arm64 manifests. Windows runs the amd64 Linux container through Docker Desktop.
- Real-image synthetic credential tests passed on both architectures. Windows verified native bind mounts, an unchanged read-only credential source, pre-onboarding import, provider credential resolution and `0600` store permissions. No real account tokens were used by these tests.
- Fresh onboarding health and setup HTML responded on both architectures using temporary data and loopback-only ports. Probe containers and temporary data were removed. The docs route returns 404 during onboarding and is owned by the runtime's completed-setup web service.
- The self-hosted Windows workflow is manual-only, targets the existing runner labels, checks out without persisted Git credentials, and does not start or modify a UA runtime. Actionlint passed with the documented custom labels.
- The published update feed was checked from a saved UA 0.4.2 selection: it offers 0.4.4, reviews both skipped releases, flags breaking changes and rejects approval without acknowledgment.
- The Windows runner build passed tests, lint, the interactive popup probe, EXE/MSI packaging, checksums and artifact upload at commit `4fffa97`. Earlier attempts exposed Restricted PowerShell policy and a popup timeout in the runner's process context. The workflow now sets policy only for its own process and launches the GUI probe through a temporary limited-privilege interactive task. The same checkout passed in that user context, and the full workflow subsequently passed.

## Consequences and operational requirements

`updates::approve` still requires the cached review identity and acknowledgment. Update discovery does not touch Docker. Image installation pulls the exact reviewed digest before replacing an owned container, retains the same persistent mount, and records pending updates for retry. Tests cover rejection of unmanaged containers and stale or unacknowledged update requests.

Controller initialization now refuses nonempty UA data when its desktop selection file is absent. It neither reads UA file contents nor invents approval for the bundled version. Tests prove that the existing bytes stay unchanged and that a saved previous selection stays selected. Legacy installations must establish the selection with Desktop 0.4.3 or restore the host-owned file before using this build.

The reviewed direct upgrade source is the previous UA 0.4.2 digest. Earlier identities are not approved for automatic replacement by this lock. Operators must finish or abandon in-flight work and follow UA's operating notes before approving an upgrade. There is no host-side snapshot retirement or database migration.

Authenticated Windows Docker builds require the signed-in credential context. An SSH-only credential failure does not establish that the desktop account is unauthenticated. This build used an interactive task under the build account after the SSH credential lookup failed; a desktop-session GitHub CLI check succeeded.

## Remaining acceptance checks

Install the unsigned development EXE and complete the platform checklist with real credentials. Verify setup-to-chat, external browser login, workspace browsing, tray/autostart and an explicitly prepared data upgrade. These are separate from the passing isolated probes. No new skill behavior or runtime skill-template changes were needed for this desktop-host build.
