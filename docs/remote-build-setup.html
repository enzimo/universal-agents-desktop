Shared setup · repeat for each machine

Register the runners

  1. In the private repository on GitHub, open Settings → Actions → Runners → New self-hosted runner. Select the machine’s OS and CPU architecture.
  2. On that machine, sign into the build account. Create actions-runner in its home directory, then follow GitHub’s download, checksum and extraction instructions there.
  3. Run GitHub’s generated configuration command locally. Name the runner, for example ua-windows-x64, ua-linux-arm64 or ua-macos-arm64. Keep the default labels and add ua-build plus the platform label in this checklist. Accept _work as its working directory.
  4. On Windows, decline the service option for this desktop test setup. Start each runner as described in its final checklist step. GitHub should show it as Idle.

The registration token expires after one hour. Get a fresh command if needed. Keep it out of this page and chat. GitHub registration instructions.

Use the machines for more than one repository

For repositories in the same organization, register at organization level and restrict the runner group to approved repositories. Public repositories also need explicit approval in the installed host hook’s public_repositories list before group access is enabled. See Local CI for the event policy and installation order. Each runner process needs its own work, hook and state folders so its jobs serialize independently. Add each project’s toolchain deliberately; these hosts are persistent and jobs share their build account’s permissions.

Only run reviewed, trusted source here. Do not route untrusted fork pull requests to machines that hold package credentials or Docker access. GitHub’s self-hosted repository guidance.

Network and reboot checks

Runners initiate outbound HTTPS connections to GitHub. Allow GitHub’s documented domains and the registries/package hosts used by the project. They need no inbound GitHub webhook port. SSH remains limited to the trusted network.

Key-based Windows SSH sessions may not unlock Docker Desktop or GitHub CLI credentials, even when the desktop account is signed in. Run authenticated builds through the foreground runner in that desktop session. A credential error over SSH alone does not mean you need to sign in again.

After reboot, verify SSH, Docker and the runner again. Linux services can recover before desktop sign-in. Windows and macOS GUI testing requires the build account to sign in and start its desktop services. Disable idle system sleep on power; do not enable automatic account login just for this guide.

First CI run

Check all three machines from GitHub

Download this manual-only workflow and put it at .github/workflows/three-machine-preflight.yml in the repository. Review and commit it to the default branch. In GitHub’s Actions tab, select Three-machine preflight → Run workflow.

It checks tools and builds and runs a tiny Docker image on each machine. It does not check out source, publish images or build UA installers. It needs no secrets. Each job should pass and print UA_DOCKER_OK. If a machine is not ready yet, remove its matrix entry before running.

Review the workflow


A green preflight confirms basic tool and Docker access from the runner’s actual environment. It does not prove Windows SDK completeness, all image-build dependencies, signing, private registry access or interactive UI behavior. Native builds and end-to-end tests follow.


Queued jobs, missing tools or billing errors
If a job queues, confirm its runner is online and has every label in runs-on. If Docker works in your terminal but fails in CI, compare the user, PATH, group membership and Docker context. Restart the runner after fixing its environment. Keep the Docker Desktop account signed in on Windows and macOS.
Self-hosted registration does not fix an account-level Actions restriction. If GitHub still refuses to dispatch this workflow because of billing, the account owner must resolve that restriction. SSH builds can continue independently.


Connect the real build and test jobs
Registering these runners does not redirect the existing workflows. After preflight passes, I can update their runner labels, remove per-job administrator package installs, and verify the native builds on each host. We will keep image publishing and installer releases separate from test runs.


  1. Run the repository’s Rust tests, Clippy and JavaScript tests on each native OS.
  2. Run the native popup probe in the signed-in Windows/macOS desktop and under Xvfb on Linux. Build each native installer and record its OS and architecture.
  3. Build Docker images and run runtime tests in the runtime repository. Use its Dockerfile and lockfiles. This desktop repository consumes its reviewed image digest through runtime-lock.json.
  4. Install the development launcher and test setup, authentication, chat, new windows, logs, updates and persistence using dedicated test accounts and workspace data.


Keep test data, secrets and releases separate
Reserve these machines for testing. UA uses a fixed container name and loopback ports, so run one full UA lifecycle test at a time per Docker daemon. One runner per host serializes its jobs; do not overlap an SSH test with a CI lifecycle run. Separate OS users can still share the same Docker daemon.
Keep build caches and runner workspaces outside UA’s persistent data. Do not modify UA databases, delete app data, run global Docker cleanup or replace an unmanaged container. Plan explicit disposable test data before adding automatic lifecycle cleanup.
The public Docker probe needs no registry login. For private builds, configure registry credentials locally in a supported helper or supply narrowly scoped CI secrets through the workflow’s secret store. Use protected environments for image publishing and signing; never embed tokens in Dockerfiles or build arguments. No passwords, tokens or private keys belong in the handoff.
Unsigned Windows builds and ad-hoc signed Mac builds are development artifacts. Production macOS distribution needs Developer ID signing and notarization. Windows signing needs its own certificate or signing service. Those identities are separate from this machine-readiness setup.


Keep the machines ready over time
Keep OS patches and the runner current. Re-run preflight after Docker or toolchain updates. Monitor free disk and retain only the project caches and artifacts you need. Start with one job per host, and add parallel capacity only after containers, ports and test data are isolated. When retiring a machine, remove its runner registration and only the dedicated SSH key entry added here.

Remove only the ua-desktop-build public-key entry from the authorized-keys file used above. Preserve any unrelated keys. If SSH was enabled only for this work, stop its service and remove only the firewall rule you added. Keep it enabled if you use it for other work.
